Redesigning VEC

Verizon's enterprise self-service portal, rebuilt on Monarch 3.0 around one question: what if the AI workspace were the product, and the forms-and-tables UI were the fallback?

TELECOMENTERPRISE SAASCONVERSATIONAL AI
Ayyappan Rajendiran · Lead Experience Designer, Innova Solutions UX Modernization Team

VEC is a real, currently-in-flight engagement — a self-service portal where enterprise and SMB Wireline and Wireless customers manage orders, service inventory, repair tickets, billing, and their own users. It's paired with an internal Agent Console used by care, help-desk, and sales teams to act on a customer's behalf when self-service can't finish the job — the two share one design system because they enforce the same entitlement rules.

Stage 01
REF// VEC-01-BUSINESS

What the redesign had to be accountable for

Before any screen work started, discovery ran across the roles that actually own this product's outcomes — the business analyst tracking completion metrics, the project manager owning the delivery roadmap, the tech lead who has to build whatever gets designed, and the associate director accountable for the P&L this portal sits inside. That alignment converged on five goals the redesign is measured against.

  • Raise self-service completion — more tasks finished in the portal without an agent, measured per journey rather than per visit.
  • Deflect assisted volume — fewer calls, chats, and Agent Console transactions for tasks the portal already supports.
  • Shorten time to order — one-pass intake and visible pricing remove the rework loop between submit and provisioning.
  • Grow digital revenue — catalog, quotes, and upgrade paths become discoverable inside the workspace, not only through sales.
  • Lower cost to change — one design system across every module and both portals cuts duplicated build and QA effort.
Numeric targets were deliberately left open at this stage — the team needed the client's current baselines for completion rate, assisted volume, and order cycle time before committing to specific numbers.CONSTRAINT, STATED UP FRONT

Stage 03
REF// VEC-03-AUDIT

Turning five pain points into five audited root causes

VOC volume said where to look; the audit said why it was happening. Every pain point was walked screen-by-screen against the same two questions — what's actually causing this, and what's the smallest fix that resolves the cause rather than the symptom — before any redesign direction was proposed.

Session & Login

Audited cause: a ≤30-min inactivity timeout purges in-progress forms, and 2FA email delivery lags long enough to break the login attempt.

Fix direction: extend session duration, add local state caching, cut 2FA delivery to under 5 seconds.

Payment & Invoice

Audited cause: invoices post 8+ days late, arriving only via an async email link; the guest payment tool crashes on multi-invoice sessions with no explanatory error.

Fix direction: instant in-portal PDF download, a refactored multi-bill payment handler, specific error messages on failure.

Support Tickets

Audited cause: the fault-selection dropdown freezes the ticket wizard, tickets don't sync to the dashboard in real time, and agents can close a ticket with no customer confirmation.

Fix direction: fix the dropdown state bug, real-time API sync, a mandatory customer sign-off before resolution.

Inventory Search

Audited cause: search fields don't support wildcards, and Wireline and Wireless assets are managed in isolated views forcing repeated account switching.

Fix direction: wildcard search across every inventory table, plus a unified toggle header.

Manual Disconnect

Audited cause: disconnecting multiple lines requires 27 repeated manual steps per line, with no bulk upload path.

Fix direction: a bulk CSV/Excel disconnect tool, "copy to all lines" form controls, updated validation logic.

Across all five

The same three failure modes repeat: state gets lost (sessions, forms, sync), errors go unexplained (payments, tickets), and the interface assumes one record at a time in a product built for enterprise-scale, multi-line accounts.

Stage 06
REF// VEC-06-PRIORITY

Four technical directions, scored on the same axes

The redesign could have gone four different technical routes to fix the "consistent experience" problem. Each was scored on effort to ship versus how strategically it set up the AI-first direction — not picked by preference.

Low effort / Low strategic value
  • Embedded Wrapper — iframe container, zero changes needed from tool teams
High effort / Low strategic value
  • No candidate scored here — every option had a strategic angle
Low effort / High strategic value
  • Design System SDK — shared token library, tools feel native — chosen for Phase 1–2
High effort / High strategic value
  • AI Abstraction Layer — AI queries tool APIs directly, no UI inconsistency possible
  • Micro-Frontend Shell — full Module Federation rebuild, fully consistent UX and shared state

The chosen path takes the low-effort, high-value option first (the shared design system) while keeping the two higher-effort, higher-value options — the AI abstraction layer and the micro-frontend shell — as the Phase 2–3 direction once the foundation is in place. The broader rollout uses the same logic at portfolio scale: a five-phase plan (Unify → Optimize → Modernize → AI-Enable → Future-Ready) that opens with a formal complexity/priority assessment across every application before committing engineering effort.

Stage 07
REF// VEC-07-USERFLOW

From a routing bot to a workspace that acts

The clearest before/after in the whole redesign is how a support conversation actually resolves.

Today (BAU)

A scripted bot asks which module the issue belongs to, deflects simple cases with FAQ content, and routes everything else to a queue. It routes conversations — it does not complete tasks, and it appears twice on the same screen.

Proposed (Conversational AI)

The AI workspace becomes the primary surface, with the structured portal UI kept as a full fallback and a live context panel alongside it. The assistant acts, not just routes.

Ask in plain language→Act, with guardrails→Explain and cite→Hand off with context

Each step is a real constraint from the redesign: requests like "why is this circuit down?" or "pay the overdue invoice" replace learning eight module menus; every action stays inside the same entitlement rules as the structured UI, with confirmation before it commits; every answer links back to the record it came from — invoice, ticket, order — so trust is verifiable, not assumed; and when a case does need a human agent, the Agent Console receives the full transcript and state, so the customer never repeats themselves.

The interactive prototype spells out exactly which flows moved where. Eight BAU flows were mapped screen-by-screen — Dashboard, Order Creation, Bill Payment (both logged-in and guest), Service Change Request, a dedicated flow for the do-not-move exception case, the Session Issue flow, Support Ticket Closure (including the sub-flow for a carrier-closed ticket and a customer request for more information), and the manual disconnect flow. The Conversational AI track covers the five highest-value flows first — Dashboard, Order Creation, Upgrade/Change/Order Status, Product Tools, and Bill Payments — deliberately narrower than BAU's eight, since the AI-first surface ships in phases rather than replacing everything on day one.

Stage 08
REF// VEC-08-IA

One shell, eight modules, one shared design system

The IA problem wasn't module count — eight modules is reasonable for what this product does. It was that each module had drifted into its own visual language, its own navigation pattern, and in places its own separate mobile treatment. The architecture direction rebuilds the portal as a Module Federation host: a shared shell (navigation, entitlement, the AI assistant) with each module registering into it as an independent, isolated unit sharing one design system.

  • Shared shell — top nav, breadcrumb, entitlement context, and the AI assistant stay visible above every module.
  • Eight modules as federated units — Dashboard, Orders, Services, Repairs, Product Tools, Billing, Users, and Support, each built and shipped independently.
  • One token library — a shared design-system package maps components and primitives so every module — and the internal Agent Console — renders from the same source of truth.
  • Two portals, one architecture — the customer-facing VEC and the internal Agent Console differ only in entitlement scope, not in structure.
Stage 09
REF// VEC-09-VISUAL

Three panels, one screen

The target layout puts three things on screen at once, in a fixed hierarchy: the AI workspace as the primary conversational surface, the structured UI (forms, tables, maps) as a fallback that never disappears, and a live context panel of ambient metrics — so a customer working with the assistant never loses the option to drop into a table and verify it themselves.

Key Learnings

The chatbot wasn't the problem — its ceiling was

The existing assistant already handled simple routing fine. The redesign wasn't "add AI," it was "let the AI actually finish the task instead of forwarding it."

Affinity clusters and business goals should argue with each other

"Deflect assisted volume" as a business goal and "silent ticket closures" as a customer pain point are the same problem seen from two sides — the redesign had to satisfy both readings at once, not pick one.

Confidentiality is a design constraint too

Writing this case study honestly — real numbers, real names where cleared, recreated rather than copied screens — took the same discipline as the redesign itself: say exactly what's true, and mark plainly what isn't shown.
